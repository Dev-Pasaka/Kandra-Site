# 05. Routes

[Page 04](/tutorial/04-plugin-install) got the plugin installed and the tables created. This page
adds the first real HTTP routes: create a todo, list "my todos," mark one done, delete one.

<Callout kind="note" title="Auth is out of scope — on purpose, stated plainly">
This tutorial does not build authentication or session management. Every route below trusts an
`X-User-Id` header as a stand-in for "the logged-in user's ID." A real app would derive that from a
verified session/JWT, not a client-supplied header anyone can forge — that's a real, separate
problem this tutorial isn't solving, not a corner quietly cut without saying so.
</Callout>

## Request/response shapes

```kotlin title="routes/TodoDtos.kt"
package com.example.todos.routes

import com.example.todos.model.UUIDSerializer
import kotlinx.serialization.Serializable
import java.util.UUID

@Serializable
data class CreateTodoRequest(
    val title: String,
    @Serializable(with = UUIDSerializer::class) val assigneeId: UUID? = null,
)

@Serializable
data class TodoPage(
    val items: List<com.example.todos.model.Todo>,
    val nextPageToken: String?,
    val hasMore: Boolean,
)
```

`KandraPage<T>` (what `findPage` returns) isn't itself a `kotlinx.serialization` type — it's a plain
Kandra runtime class — so routes map it into this small local DTO before responding, rather than
trying to serialize it directly.

## The routes

```kotlin title="routes/TodoRoutes.kt"
package com.example.todos.routes

import com.example.todos.model.Todo
import com.example.todos.model.TodoTable
import io.kandra.ktor.kandra
import io.ktor.http.*
import io.ktor.server.application.*
import io.ktor.server.request.*
import io.ktor.server.response.*
import io.ktor.server.routing.*
import java.time.Instant
import java.time.temporal.ChronoUnit
import java.util.UUID

fun Route.todoRoutes() {
    val todoRepo = application.kandra.suspendRepository<Todo>()

    post("/todos") {
        val ownerId = call.ownerIdOrRespondBadRequest() ?: return@post
        val req = call.receive<CreateTodoRequest>()

        val todo = Todo(
            ownerId = ownerId,
            createdAt = Instant.now().truncatedTo(ChronoUnit.MILLIS),
            todoId = UUID.randomUUID(),
            title = req.title,
            assigneeId = req.assigneeId,
        )
        todoRepo.save(todo)
        call.respond(HttpStatusCode.Created, todo)
    }

    get("/todos/mine") {
        val ownerId = call.ownerIdOrRespondBadRequest() ?: return@get
        val pageSize = call.request.queryParameters["size"]?.toIntOrNull() ?: 20
        val token = call.request.queryParameters["token"]

        val page = todoRepo.findPage(pageSize, token) { TodoTable.ownerId eq ownerId }
        call.respond(TodoPage(page.items, page.nextPageToken, page.hasMore))
    }

    patch("/todos/{createdAt}/{todoId}/done") {
        val ownerId = call.ownerIdOrRespondBadRequest() ?: return@patch
        val createdAt = Instant.parse(call.parameters["createdAt"]!!)
        val todoId = UUID.fromString(call.parameters["todoId"]!!)

        val existing = todoRepo.findById(ownerId, createdAt, todoId)
            ?: return@patch call.respond(HttpStatusCode.NotFound)

        todoRepo.update(existing, existing.copy(done = true))
        call.respond(existing.copy(done = true))
    }

    delete("/todos/{createdAt}/{todoId}") {
        val ownerId = call.ownerIdOrRespondBadRequest() ?: return@delete
        val createdAt = Instant.parse(call.parameters["createdAt"]!!)
        val todoId = UUID.fromString(call.parameters["todoId"]!!)

        val existing = todoRepo.findById(ownerId, createdAt, todoId)
            ?: return@delete call.respond(HttpStatusCode.NotFound)

        todoRepo.delete(existing)
        call.respond(HttpStatusCode.NoContent)
    }
}

private suspend fun ApplicationCall.ownerIdOrRespondBadRequest(): UUID? {
    val raw = request.headers["X-User-Id"]
    val parsed = raw?.let { runCatching { UUID.fromString(it) }.getOrNull() }
    if (parsed == null) respond(HttpStatusCode.BadRequest, "Missing or invalid X-User-Id header")
    return parsed
}
```

## `POST /todos` — create

Ordinary `save()` — no `@LookupIndex`, no batch, nothing exotic. `createdAt = Instant.now().truncatedTo(ChronoUnit.MILLIS)` is set
right here, once, by application code, per [page 03](/tutorial/03-entities)'s resolution: this is the
value that becomes the row's clustering key, and it's the same value the response body hands back to
the caller so they can address this exact todo later.

<Callout kind="gotcha" title="Truncate to milliseconds — Cassandra's timestamp does">
`Instant.now()` has microsecond precision on most JVMs, but a CQL `timestamp` stores milliseconds. If you hand the caller the untruncated value, the
row still resolves (the codec truncates on the way in), but anything keyed on the *caller-supplied* `Instant` no longer matches the entity read back
from the database — most visibly the `@CacheResult` cache that `findById` fills (page 10): `update()` invalidates by the stored millisecond key, so
the stale cached entry survives and the next optimistic-locked update fails with a spurious `409`. Truncating once, where the todo is created, avoids
that class of bug entirely.
</Callout>

<Callout kind="note" title="Fixed in 0.5.1">
From 0.5.1 the cache normalizes `Instant` keys to milliseconds itself ([#178](https://github.com/Dev-Pasaka/kandra/issues/178)), so the stale-entry problem above
no longer occurs. On 0.5.0 and earlier, truncating is required. Truncating where the todo is created is still the cleaner habit, since the value you return
to clients then matches what is stored.
</Callout>

## `GET /todos/mine` — the cheapest read this app has

```kotlin
todoRepo.findPage(pageSize, token) { TodoTable.ownerId eq ownerId }
```

A partition-scoped range read with driver-native paging — no `ALLOW FILTERING`, no scatter-gather,
exactly the query shape `Todo`'s partition/clustering design in
[page 01](/tutorial/01-modeling) exists to make cheap. Results come back newest-first with zero sort
logic in this handler, because `@ClusteringKey(order = DESC)` already baked that ordering into the
table.

## `PATCH /todos/{createdAt}/{todoId}/done` and `DELETE /todos/{createdAt}/{todoId}` — why the URL carries the key

<Callout kind="tip" title="Ties back to page 01: there's no single 'the primary key'">
`Todo` has no single-column ID a route could look it up by directly. `todoId` is part of the key
(per [page 03](/tutorial/03-entities)) but only after `createdAt`, so there's no way to find a row
by `todoId` alone without a full scan Kandra won't build. What identifies one todo is the full key
`(ownerId, createdAt, todoId)`: the owner comes from the `X-User-Id` header on every route in this
app, and the URL carries the two clustering columns, `createdAt` as ISO-8601 (parsed with
`Instant.parse(...)`) and `todoId` as a UUID. Both come straight from the create response.
</Callout>

Both handlers do the same two-step: `findById(ownerId, createdAt, todoId)` to load the exact row (a single-
row point lookup, not a scan — `findById` requires the *full* key, partition then clustering, in
schema order, or it throws rather than guessing), then act on the loaded entity.

**`PATCH /todos/{createdAt}/{todoId}/done`** calls `todoRepo.update(existing, existing.copy(done = true))`. Right
now, with no `@Version` column on `Todo` yet, `update(old, new)` performs a blind full-row overwrite
— no concurrency check of any kind. If two requests race to mark the same todo done at nearly the
same instant, both succeed, and whichever's write lands last simply wins; nothing detects the race.
That's a real gap, left deliberately unfixed here — [page 07](/tutorial/07-concurrency) adds
`@Version` to `Todo` and this exact call site starts enforcing a real compare-and-set, with no other
code in this handler changing.

**`DELETE /todos/{createdAt}/{todoId}`** calls `todoRepo.delete(existing)` — a genuine, permanent `DELETE` right now,
since `Todo` has no `@SoftDelete` yet. [Page 08](/tutorial/08-soft-delete-and-trash) adds a 7-day
undo window; this same `delete()` call is what changes behavior once that annotation lands, again
with no route code changing.

<Callout kind="tip">
Verify the checkpoint: `POST /todos` with a title, `GET /todos/mine` with the same `X-User-Id`
should return it, `PATCH /todos/{createdAt}/{todoId}/done` (using the `createdAt` and `todoId` from the create response) should
flip `done`, and `DELETE /todos/{createdAt}/{todoId}` should make it disappear from `GET /todos/mine`.
</Callout>
